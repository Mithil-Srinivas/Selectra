Selectra

A product search and shopping assistant for a fixed 5,000-product catalogue and a 30-section store policy. Shoppers write short, misspelt, often Hinglish questions. The assistant must answer, ask which product they mean, or refuse, and every fact it states must come from the catalogue or the policy.

What we are scored on

Each of the 150 test questions needs one action: answer, clarify or refuse. The official evaluate.py scores every question like this:

question_score = action_correct × (0.4 + 0.3 × grounded + 0.3 × helpful) − 3 × hallucinated_prices
−3for every price not copied from the catalogue
≤ 10cited products, or product credit is lost
0.73baseline score on the 40 dev questions
20%of judging is this score; the rest is framing, soundness, usability, responsibility, demo

The rule everything follows

The LLM interprets the question. Code checks every fact against the catalogue. The catalogue decides.

The language model never sees a price and never writes one. It turns the shopper's words into a structured search plan. Everything after that is deterministic code that reads the catalogue record, so any value we show can be traced to a field in a specific product.

How a question flows through the system

Decisions we made, and the evidence

DecisionWhy
LLM firstDescriptions such as “baal sukhane wali machine” fail with embeddings alone: hit@1 rose from 0.51 to 0.89 when the LLM interprets first.
Search twice, then fuseThe LLM's phrase alone loses named products (dev hit@1 0.85 vs 0.93 for raw text). Fusing both keeps the best of each.
Catalogue picks the sub-categoryThe LLM guesses product types from brand names wrongly (“Funkari TerraFusion” called a jigsaw puzzle). Trusting it alone cut named-product hit@1 to 0.78.
No rerankerA correct product is already in the top 30 for every probe query. A reranker scores relevance and cannot tell a 50 ml from a 150 ml variant, which is a clarify case.
No vector database5,000 × 1,024 floats is about 20 MB; a NumPy dot product over all of it takes about 1 ms.
LLM thinking offThinking mode used about 2,000 tokens and 28 s per question with no better JSON. Without it: about 120 output tokens.

Stack

  • LLM: Qwen3.5-9B Instruct, GGUF Q4_K_M, served by Ollama on a LAN GPU server. Thinking off, 8,192-token context.
  • Embeddings: qwen3-embedding:0.6b, 1,024 dimensions, normalised. Instruction prefix on queries only.
  • Index: NumPy matrix cached as .npy; rebuilt automatically when the catalogue or model changes.
  • Also: RapidFuzz for names, Pydantic for the plan schema, NiceGUI for the UI, uv with Python 3.13.

Known risks

  • Offline rule. Models must run offline during judging. Confirm with the organisers that a LAN server counts.
  • Server stability. On 30 Oct the GPU slowed from 73 to about 16 tokens/s and crashed once with a CUDA error. Check it before any demo.
  • Material words. The LLM sometimes drops a material (“red silk saree”). Colour has a code backstop; material does not yet.
  • Small labelled set. Only 40 dev questions have answers. Our probe sets are self-written, so their numbers may flatter us.
